Password vault

Keep passwords in an encrypted vault on a FIDO2 key, opened with the key's PIN and a touch — in the desktop app's Vault tab, or with keyroostctl fido vault.

Experimental

Experimental: please report problems and keep a backup.

What it is

A vault is a FIDO2 credential on the key, for the relying party fido2-vault.token2. Its entries each hold a title, a username, a web address, notes and a password. They are sealed with a secret the key gives out only after the PIN and a touch, and stored in the key's large-blob store. A key can hold several vaults, each with its own name.

A vault lives only on its key: if the key is lost or reset, the vault goes with it. Keep a backup file (below).

A key can hold a vault when it has a large-blob store, the hmac-secret, largeBlobKey and credProtect extensions, credential management, CTAP 2.1 permission tokens, and a PIN that is set. In the app, a key without them gets no Vault tab, and the Password vault card on its Overview says why. A key with no PIN yet can set one on the FIDO2 tab.

Unlocking

Open the Vault tab, next to Authenticator, or Manage on the Overview's Password vault card. Enter the key's FIDO2 PIN, then touch the key once. On a key that holds no vault yet, no touch is needed.

One PIN entry serves both tabs. When the FIDO2 tab is already unlocked, the Vault tab uses its PIN; a PIN typed in the Vault tab also unlocks the FIDO2 tab. Each vault unlock still asks for its touch. Lock locks only the tab it is on.

The top bar's Refresh reads the open vaults again with no PIN and no touch, so a change made by another program shows. A vault made elsewhere appears after Lock and Unlock.

The vault locks with the rest of the app after 5 minutes without use. While an entry form has unsaved changes, the vault alone stays open for up to 15 minutes, so a half-typed entry isn't lost; every other tab still locks at 5 minutes.

A vault that can't be opened is listed as NAME · (unavailable), and the tab says why. It can't be changed, but it can still be deleted; the key's other vaults work as usual.

Entries

Each vault is listed with its name and how many entries it holds. Pick one to see its entries; Filter entries… narrows a long list.

Add entry opens a form with Title, Username, Password, URL and Notes. Generate makes up a password: 20 characters from A–Z, a–z, 0–9 and symbols, unless you change the length or the character sets. Save writes the vault back to the key with no touch; the PIN is already entered.

An opened entry shows its web address and notes, and when it last changed. The password stays hidden until Show. Edit opens the same form; Delete asks first, and needs no touch.

Two entries may share a title. The list tells them apart by username and web address.

Every write reads the key first. If an entry changed on the key since the vault was opened (from the command line, say), nothing is written: the list shows the entry as the key now holds it, and the form keeps what you typed so you can check it and save again. A change made elsewhere is never overwritten without you seeing it.

Copying a username or password

Copy username and Copy password put it on the clipboard. keyroost clears it after 45 seconds if the clipboard still holds it, and at once when the vault locks; text you copied since is left alone.

The copy is marked to stay out of clipboard history on macOS, Windows and X11. A native Wayland window copies it unmarked, and where the app can't read the clipboard it leaves it as it is rather than risk clearing something else.

Backups

Because a vault lives only on its key, keep a backup file, protected by a passphrase. Export backup… asks where to save the file, then for the passphrase twice. It needs at least 10 characters. Without it, the backup can't be opened.

The file opens with its passphrase alone, without the key: keep the two apart. The backup is written from the unlocked vault, with no touch. Bring it back with Import backup…, on the same key or another.

Importing a backup

Import backup… asks for the file and its passphrase, then for the vault to bring the entries into: one on the key, or A new vault named…. Each entry in the backup becomes a row:

  • add — the vault doesn't have it. Ticked.
  • replace — the backup's copy is newer. Ticked. A row whose copy on the key is newer replaces it only if you tick it.
  • exists — already in the vault; left as is. It has no box.
  • skip — not ticked, the key's copy is newer, or this build can't tell how it compares.

Any row with a box can be ticked or unticked, or use Tick all and Untick all; the line under the list counts what will happen. Importing into a vault on the key needs no touch. Into a new vault, the button says it creates the vault: that takes two touches, then the entries go in.

The rows and reasons are the same as fido vault import on the command line, which uses --replace and --entry where the app uses ticks.

Creating, rotating and deleting vaults

+ New vault asks for a name; Create vault takes two touches.

Rotate vault key… gives this vault a new key. Use it after unlocking the vault on a computer you no longer trust, then change the passwords that matter. A new vault of the same name takes the entries, and the old one is deleted after every entry is checked. It takes two touches. If the vault changes on the key meanwhile, nothing is rotated and the list shows the vault as it is now.

Delete vault… deletes the vault and its entries, and can't be undone. It asks first and offers Export backup… before you confirm. It uses the PIN already entered and needs no touch.

Space on the key

The large-blob store is shared space on the key, meant for data that belongs to a passkey; each vault is kept there as the data of its own credential. Websites may store data there too, so keep vaults small.

A save, create, rotate or import that doesn't fit is refused before any touch, with the numbers, and nothing is written. One that fits but leaves less than a quarter of the store free still goes ahead, and the activity log and status bar say how full the store is.

A name or note kept on the key belongs to no passkey, so a browser may clear it when the store is full and a website needs room (see Storage). A vault belongs to its own credential, so that doesn't apply to it.

The store can be read without the PIN. Anyone holding the key can see roughly how large the vault is, not what is in it. Once a vault is unlocked, the Storage tab names its entry password vault "NAME" (encrypted).

Command line

keyroostctl fido vault list                    # asks for the PIN (hidden), then a touch
keyroostctl fido vault add Personal            # a new vault (two touches)
keyroostctl fido vault entry add GitHub --username alice --generate-password
keyroostctl fido vault entry show GitHub --reveal
keyroostctl fido vault export Personal -o personal.t2vault
keyroostctl fido vault import -i personal.t2vault --dry-run   # preview; writes nothing
keyroostctl fido vault rotate Personal         # asks y/N

The app and the command line use the same words for the same thing. Every fido vault command is listed in the command reference.

Where the format comes from

The vault design and its formats (the vault data on the key and the backup file) come from Token2's FidoParole. Token2 approved their reuse in keyroost in discussion #74; thank you, Token2. keyroost is an independent implementation that reads and writes the same bytes, checked against FidoParole's own vault code and libfido2.
